## 1. 技术研究项目四阶段流水线

**通用公式**：

```
数据采集 → 洞察分析 → 框架构建与验证 → 优化与机会评估
   ↓           ↓            ↓                ↓
 原始事实    模式识别     标准化工具       可落地方向
```

| 阶段 | 输入 | 产出 | 质量标准 |
|------|------|------|----------|
| 数据采集 | 目标 URL / 文档 | 结构化数据 + 截图 | 数据完整 ≥ 90% |
| 洞察分析 | 结构化数据 | 报告 + N 条洞察 | 每条有证据链 + 推论 |
| 框架构建 | 洞察结论 | 检查清单 + 评分体系 | 权重合理、边界值自洽 |
| 优化评估 | 框架评分结果 | 优化方案 + 机会清单 | 有预算影响、有优先级 |

**可复用规则**：
- 阶段间不可跳跃：没有数据采集就直接框架构建 = 空中楼阁
- 每阶段必须有验证动作（数据完整性校验 / 评分边界值测试 / 预算对比）
- 最终产物必须形成闭环（洞察 → 框架 → 优化 → 可落地方向）

## 2. 研究框架设计三原则

**从 TRAE 实践提炼**：

### 原则 1：维度权重按战略重要性分配，绝不均分

```
正确：产品植入 30% > 增长漏斗 25% > 奖金体系 20% > 评审机制 15% > 赛道设计 10%
错误：5 个维度各 20%
```

**推论**：均分权重 = 回避判断 = 框架失去区分度。敢于分配不等权重，本身就是研究结论的一部分。

### 原则 2：每维度 5 个检查点

- **< 3 个**：区分度不足，同一维度的不同评估对象趋同
- **> 7 个**：粒度冗余，评分疲劳
- **5 个**：恰好覆盖核心要素，单维度评分可在 2 分钟内完成

### 原则 3：评分必须可验证

- 每个检查点有 4 级预期值（如"强制要求 / 推荐使用 / 无要求"），而非纯主观 1-5 分
- 框架首次使用前必须跑边界值测试（全 1 分 / 全 5 分 / 全 3 分）
- 首次模拟评分后必须交叉验证（多人独立评分 → 对比分歧）

## 3. 优化方案汇报四段式

**通用公式**（每次向上汇报优化方案时套用）：

```
段 1：现状问题 — 用数据/评分说话，不凭感觉
段 2：优化方案 — 给出具体可操作的新方案
段 3：预算影响 — 必须算账（多少钱、从哪出）
段 4：预期收益 — 量化改善（评分从 X → Y）
```

**增强技巧**：
- "预算零增长"比"需要更多预算"好 10 倍 —— 说明你做了内部再分配而非伸手要钱
- Mermaid 图表替代纯文字表格 —— 视觉传达效率高，领导层扫一眼就懂
- 每个方案必须有「风险与对策」附段 —— 证明你思考过失败场景

## 4. 问题模式库：四种典型障碍及解法

| 问题模式 | 典型症状 | 通用解法 | 适用场景 |
|----------|----------|----------|----------|
| **工具不适配** | 静态工具在 SPA 上返回空 | 降级→升级：先确认失败原因，再切换更强大的工具 | 任何涉及外部系统交互的任务 |
| **数据膨胀** | 结果数量远超预期且含大量重复 | 切换数据提取粒度（DOM → innerText） | 网页抓取、日志分析 |
| **Shell 差异** | 跨平台命令报错 | 先区分"阻断性错误"和"非阻断性警告"，忽略后者 | Windows/Linux 交叉开发 |
| **编码损坏** | 文件读取为乱码 | 不影响核心分析则标注跳过；关键数据回溯原始源 | 多环节文件流转 |

**可复用规则**：
- 每个问题记录格式：现象 → 根因 → 解法 → 影响评估（是否阻断）
- 不求完美解决所有问题，但求不丢失核心数据

## 5. 工具链选型矩阵

根据 TRAE 项目实际使用效果，整理跨项目可参考的工具选型：

| 场景 | 推荐工具 | 替代方案 | 选型依据 |
|------|----------|----------|----------|
| 静态网页抓取 | defuddle | WebFetch | 轻量优先，失败再升级 |
| SPA 动态抓取 | agent-browser | Playwright | 内置 wait networkidle，与 IDE 集成更好 |
| 文件写入（跨平台） | Write 工具 | Python 脚本 | 绕过 PowerShell 字符串转义陷阱 |
| 评分逻辑验证 | Python 一行脚本 | 手算 | 避免人工计算错误，结果可复现 |
| 归档操作 | Python shutil | 手动复制 | 批量操作，错误率低 |
| 任务追踪 | TodoWrite | 无 | ≥ 3 步任务必须用，防止遗漏 |

**关键教训**：**不要在 PowerShell 中用 Python -c 写多行字符串**。嵌套引号转义是已知陷阱，改用 Write 工具或独立 .py 文件。

## 6. 文档生命周期管理

**来自本项目从 10 个 temp 文件 → 归档 → 清理的实践**：

| 阶段 | 动作 | 决策标准 |
|------|------|----------|
| **产生** | 放入 `.temp/` | 所有中间产物默认位置 |
| **归档** | 复制到 `.archive/{project}-{date}/` | 有长期引用价值的数据/报告 |
| **萃取** | 提炼到 `.agents/docs/references/` | 可跨项目复用的方法论/公式/原则 |
| **清理** | 删除 `.temp/` 原始文件 | 确认归档副本存在 + 下游产物不依赖 |

**可复用规则**：
- 一个研究项目完成后，.temp/ 中留存文件不应超过原始数量的 30%
- 归档前自问：一年后有人接手类似任务，哪个文件能让他少走弯路？只保留那些
- 萃取是归档的真子集：归档 = 完整留档；萃取 = 只保留公式/原则/模式

## 7. 多轮复盘中的信息递减管理

**实践观察**：本项目经历了 3 次总结（洞察报告 → 第一次复盘 → 最终复盘），每次都在前一次基础上精简。

**通用原则**：

```
原始数据（100%） → 洞察报告（30%） → 复盘报告（15%） → 萃取文档（5%）
                    ↑                    ↑                  ↑
                 删细节留结论         删过程留决策         删案例留公式
```

**判断标准**：
- 如果第 N+1 次总结篇幅 ≥ 第 N 次，说明有冗余或未做减法
- 萃取文档的目标长度：每个洞察 ≤ 10 行，全篇 ≤ 200 行
- 当萃取文档中出现具体案例名称（如"TRAE""字节"），检查是否可替换为通用表述

## 8. 研究类任务的投入产出比评估

| 投入 | 产出 | 产出可复用性 |
|------|------|-------------|
| 数据采集（8min） | 结构化数据 + 截图 | 低（一次性） |
| 洞察分析（10min） | 5 条洞察 | 中（同类对象可对照） |
| 框架构建（15min） | 5 维 25 项清单 | **高**（任何竞品可复用） |
| 优化方案（10min） | 2 个方案 + 汇报材料 | 中（方法论可复用） |
| 机会评估（8min） | 5 个落地方向 | 低（领域相关） |
| 萃取沉淀（5min） | 8 条通用方法论 | **高**（任何技术研究项目） |

**推论**：投入产出比最高的两件事是「框架构建」和「萃取沉淀」—— 前者产出可复用工具，后者产出可复用方法。每次研究项目至少应完成这两步才叫闭环。
