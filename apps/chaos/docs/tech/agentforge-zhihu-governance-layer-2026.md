# AI Agent 时代，真正缺的不是框架，而是“治理层”

> 本文改写自 `agentforge-competitive-analysis-2026.md` 的竞品分析、复盘与后续洞察，面向知乎读者做一次更易读的公开表达。

如果你最近关注 AI Agent，大概率已经听过 LangChain、LangGraph、CrewAI、AutoGen、Dify、OpenAI Agents SDK。

它们解决的问题，大多可以概括为一句话：

> 怎么让 Agent 跑起来？

比如：

- 怎么接模型？
- 怎么接工具？
- 怎么做多 Agent 编排？
- 怎么做记忆？
- 怎么做工作流？
- 怎么做可视化搭建？

这些当然重要。但我最近在做 AgentForge 的竞品分析时，越来越强烈地意识到：

> AI Agent 真正进入团队协作和企业生产环境之后，最稀缺的能力，可能不是“再多一个运行时框架”，而是一个能让 Agent 项目被治理、被审计、被验证的工程层。

这就是 AgentForge 想解决的问题。

---

## 一、先纠正一个常见误解：AgentForge 不是“又一个 Agent 框架”

很多人第一次看 AgentForge，容易把它放进 LangChain、CrewAI、AutoGen、Dify 这一类框架里比较。

但这个比较坐标系本身就是错的。

LangChain、CrewAI、AutoGen、Dify 关心的是：

> Agent 如何执行任务？

AgentForge 关心的是：

> Agent 项目如何被组织、约束、审计和验证？

换句话说：

- LangChain / CrewAI / AutoGen 让 Agent 跑起来；
- AgentForge 让 Agent 守规矩；
- Inkog 这类工具更偏向检查 Agent 是否真的守规矩。

所以 AgentForge 和主流 Agent 运行时框架不是替代关系，而是上下层关系。

更准确地说：

> AgentForge 不是 Agent 的发动机，而是 Agent 项目的“治理结构”。

---

## 二、为什么“治理层”会变得重要？

在个人试验阶段，一个 Agent 能调用工具、能写代码、能完成任务，就已经很有价值。

但一旦进入团队和企业场景，问题会立刻变复杂。

你会遇到这些问题：

1. 不同 AI IDE 读到的项目规则不一致；
2. Agent 不知道哪些动作必须人工审批；
3. 多个 Agent 之间职责边界不清；
4. 高风险操作没有审计记录；
5. LLM 输入输出没有脱敏与净化；
6. 出问题后无法解释“当时为什么这么做”；
7. 面对合规或采购审查时，无法证明系统受控。

这时，问题已经不是“有没有 Agent 框架”了，而是：

> 你的 Agent 项目有没有一套可被人和机器共同理解的治理协议？

这也是 AgentForge 与运行时框架的本质区别。

运行时框架更像“业务代码怎么跑”。

AgentForge 更像“这个项目里的 AI 应该遵循什么宪法”。

---

## 三、AGENTS.md 是入口，但还不够

AGENTS.md 是一个非常重要的变化。

它的价值在于：你只要在项目根目录放一个 `AGENTS.md`，不同 AI 编程工具就可以读取这个项目的指令。

这让 AI 项目第一次有了类似“README for Agents”的入口。

但仅有 AGENTS.md 还不够。

因为真实项目里，规则会变多：

- 前端规则；
- 后端规则；
- Python 规则；
- 安全规则；
- 文档规则；
- 测试规则；
- 多 Agent 协作规则；
- 高风险操作审批规则。

如果全部塞进一个 AGENTS.md，最后就会变成一份又长又重、所有 Agent 每次都要读的“大杂烩”。

AgentForge 的做法是：

```text
AGENTS.md                 项目级入口与路由
.agents/rules/            领域规则
.agents/skills/           可复用技能
world.toml                声明式资产清单
constraints.toml          操作约束与治理声明
Team / Role / Agent       多智能体协作元模型
```

这不是在替代 AGENTS.md，而是在把 AGENTS.md 结构化、模块化、可治理化。

一句话：

> AGENTS.md 告诉 Agent “从哪里开始读”；AgentForge 告诉项目“规则如何组织、分发、执行和验证”。

---

## 四、真正的竞争对手不是 LangChain，而是“大家还没意识到需要治理”

这次竞品分析里，一个很重要的复盘结论是：

> AgentForge 最大的风险不是被 LangChain、CrewAI 或 AutoGen 打败，而是用户根本没有意识到自己需要治理层。

这很现实。

早期用户更容易为“可见功能”买单：

- 能不能调用工具？
- 能不能跑工作流？
- 能不能做 RAG？
- 能不能可视化编排？

但治理层的价值往往在出问题后才显现：

- Agent 删除了不该删的文件；
- 多个工具使用了不同规则；
- 安全团队问不清审计链路；
- 法务问不清人类监督机制；
- 项目迁移后 AI 规则全部失效；
- 新成员接入后不知道 Agent 的职责边界。

所以 AgentForge 的市场教育，不应该说：

> 我们比 LangChain 更强。

而应该说：

> 当 Agent 从单点试验走向团队协作和合规运营时，运行时框架之外还需要治理层。

这是两个完全不同的叙事。

前者会把自己拖进运行时框架竞争；后者才能建立新类别。

---

## 五、声明层不是终点，治理必须形成闭环

复盘中另一个重要洞察是：

> 配置不是能力，声明不是治理本身。

比如你在配置里写：

```text
audit_all_actions = true
require_human_approval_for = ["delete", "deploy", "payment"]
sanitize_llm_input = true
```

这当然有价值，但它只说明“项目声明自己想这样做”。

真正的问题是：

- 审计真的发生了吗？
- 高风险动作真的被拦截了吗？
- 人类审批真的进入链路了吗？
- LLM 输入真的被净化了吗？
- CI 能验证这些声明和行为一致吗？

所以 AgentForge 的能力不应停留在“协议定义”，而应升级为三层治理闭环：

```text
声明层：AGENTS.md / world.toml / constraints.toml
执行层：审计、审批、净化、协作路由等真实机制
验证层：本地校验脚本、CI 门禁、合规评分、行为审计
```

这也是 AgentForge 后续最重要的演进方向。

它不能只成为一个“写得很漂亮的规范目录”。

它必须能帮助项目回答：

> 我们声明了什么？执行了什么？如何证明执行结果与声明一致？

## 六、EU AI Act 不是噱头，而是现实催化剂

很多技术项目谈合规时，容易把它当成营销词。

但在 AI Agent 场景里，EU AI Act 这类法规会真实改变企业采购和工程落地逻辑。

企业会被迫回答这些问题：

- 高风险动作是否有人类监督？
- 关键操作是否可追溯？
- 模型输入是否经过必要净化？
- 系统行为是否有审计记录？
- 出问题后是否能复盘责任链路？

这类问题不是运行时框架天然解决的。

LangChain 可以让 Agent 调工具，CrewAI 可以让 Agent 组队，Dify 可以让工作流可视化，但它们不天然回答：

> 这个 Agent 项目如何证明自己是受控的？

这正是治理层的机会。

所以 AgentForge 更准确的定位应该是：

> AgentForge 不只是 AGENTS.md 的结构化扩展，更是把治理要求翻译成项目级工程结构的轻量承载层。

这个定义比“Agent 治理协议标准”更接近企业真实动机。

因为它回答的是“为什么现在要做”。

## 七、AgentForge 和 Inkog 的关系：不是简单竞品，更像上下游

在 Agent 治理方向，Inkog 是少数值得认真对标的项目。

但二者也不是完全同层竞争。

可以这样理解：

- AgentForge 偏上游：定义项目如何表达治理结构；
- Inkog 偏下游：检查项目是否真的遵守治理声明。

也就是说，AgentForge 更像协议层，Inkog 更像校验层。

一个回答“应该如何定义”，一个回答“有没有做到”。

这反而意味着二者有互补空间。

未来真正有价值的组合可能是：

```text
AgentForge 定义治理结构
Inkog / CI / 本地脚本验证治理执行情况
运行时框架负责业务执行
```

这样才是一个完整的 Agent 工程体系。

---

## 八、北极星指标也要升级：不只看采用量，还要看闭环度

很多开源项目喜欢看 Stars、下载量、项目采用数。

这些指标重要，但对 AgentForge 这种治理层项目来说还不够。

因为一个项目“用了 AGENTS.md”，和一个项目“形成声明、执行、验证闭环”，价值完全不同。

所以更合理的指标应该包括：

| 指标 | 含义 |
|---|---|
| 声明层采用率 | 项目是否使用 AGENTS.md / constraints.toml 等声明治理结构 |
| 执行层接入率 | 审计、审批、净化等机制是否接入真实链路 |
| 验证层覆盖率 | 是否有本地校验、CI 门禁或合规检查 |
| 示范闭环项目数 | 是否存在声明、执行、验证三层完整案例 |

也就是说，AgentForge 不应只追求“多少项目用了我”，而应追求：

> 多少项目因为 AgentForge 变得更可治理、更可审计、更可验证。

这才是治理层项目真正的质量指标。

## 九、一个更准确的一句话总结

经过竞品分析和复盘，我认为 AgentForge 最准确的一句话定位是：

> AgentForge 不与 LangChain、CrewAI、AutoGen、Dify 竞争“让 Agent 跑起来”的能力；它竞争的是“如何把 Agent 项目组织成可治理、可审计、可验证的工程系统”这一空白地带。

如果说运行时框架解决的是 Agent 的“执行效率”，那 AgentForge 解决的是 Agent 项目的“组织秩序”。

前者决定 Agent 能不能干活。

后者决定 Agent 能不能进入团队、企业和合规环境。

## 十、最后：AI Agent 工程化会走向哪里？

我越来越相信，AI Agent 的工程化会经历三个阶段。

第一阶段：能跑。

大家关心模型调用、工具调用、RAG、工作流、多 Agent 编排。

第二阶段：能用。

大家关心稳定性、成本、上下文管理、任务成功率、可观测性。

第三阶段：能管。

大家开始关心规则一致性、权限边界、人类监督、审计追踪、合规证明、多工具协同。

现在大多数 Agent 框架还集中在第一、第二阶段。

但企业采用一定会把行业推向第三阶段。

到那时，问题不会再是“我该选哪个 Agent 框架”，而会变成：

> 无论我选哪个 Agent 框架，我如何保证整个 Agent 项目是可治理的？

这就是 AgentForge 想切入的位置。

它不负责替你选择发动机。

它负责让整辆车有仪表盘、刹车、驾驶规则和审计记录。

而这件事，在 Agent 真正进入生产环境之后，会变得越来越重要。
