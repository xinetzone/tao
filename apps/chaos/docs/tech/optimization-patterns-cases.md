## 规则 1：非现金补偿对冲

**定义**：任何涉及「利益重新分配」的方案，必须配套非现金补偿，降低受损方抵触。

### 案例 1-1：研发资源重分配

```
场景：CTO 决定将 3 个前端人力从「用户端迭代」抽调到「内部工具链建设」

风险：用户端团队不满——"我们迭代速度会被砍半"

应用规则：
  ❌ 错误做法：直接宣布，不加补偿
  ✅ 正确做法：
     - 现金不变（薪资不受影响）
     - 非现金补偿：
       1. 抽调期间前端团队可优先使用新工具链（吃自己的狗粮）
       2. 每月 1 次与 CTO 直接沟通的技术决策会
       3. 工具链建成后，前端团队享有 6 个月的「架构贡献者」署名权

效果：抵触 → 认可，3 人中有 2 人主动报名
```

### 案例 1-2：预算削减

```
场景：市场部年度预算从 500 万砍到 350 万

风险：各业务线争抢剩余预算，可能引发内耗

应用规则：
  ❌ 错误做法：按比例均砍，人人不满
  ✅ 正确做法：
     - 现金减少 30%
     - 非现金补偿：
       1. 预算被砍但高优先级项目获 CEO 站台背书（内部曝光价值）
       2. 优先使用公司新签的 KOL 资源池（原需单独采购）
       3. 年度预算节省部分的 20% 作为部门创新基金自由支配
     
效果：350 万实际购买力 ≈ 原来 480 万（非现金资源折算 130 万）
```

### 案例 1-3：赛道奖金差异化

```
场景：赛事将热门赛道奖金从 5 万降至 3.5 万（本次 TRAE 实践）

风险：热门赛道参赛者不满降薪

应用规则：
  ❌ 错误做法：只降不补
  ✅ 正确做法：
     - 现金：¥50,000 → ¥35,000（-30%）
     - 非现金补偿：
       1. 热门赛道 TOP 10 自动进入「字节技术导师计划」
       2. 获奖作品优先获得字节全渠道传播曝光（价值远超差价）
       3. 热门赛道参赛者额外获得 TRAE Pro+ 年卡

效果：报名热度未降，参赛者认为"曝光 + 导师"总价值 > 差价 ¥15,000
```

## 规则 2：预留浮动空间

**定义**：任何涉及「行为引导」的方案，必须预留 ≥ 10% 动态调整空间。

### 案例 2-1：功能灰度上线

```
场景：产品经理想将注册流程从 3 步改为 1 步，担心老用户不习惯

风险：改动过大导致注册放弃率反而上升

应用规则：
  ❌ 错误做法：全量上线，出问题再回滚
  ✅ 正确做法：
     - 预留 10% 流量给新版注册流程（A/B 测试）
     - 触发条件：新版放弃率 > 旧版 × 1.2 → 自动回退到 5% 流量
     - 触发条件：新版放弃率 < 旧版 × 0.8 且持续 3 天 → 扩量到 50%
     - 预留调整周期：2 周

效果：第 3 天发现移动端放弃率异常，第 4 天修复，第 7 天全量上线
```

### 案例 2-2：OKR 目标分配

```
场景：团队从「功能开发 OKR」转向「用户留存 OKR」

风险：团队可能短期忽视留存，或过度优化留存牺牲新功能

应用规则：
  ❌ 错误做法：直接设一个固定目标（如"留存提升 10%"）
  ✅ 正确做法：
     - 主目标：留存提升 10%
     - 预留 15% 权重为「季度动态调整项」
     - 触发条件（月度复盘）：
       若新功能上线速度 < 原计划的 70% → 将 5% 权重从留存回调到功能产出
       若留存已超 12% → 将 5% 权重转移到「付费转化」

效果：团队有安全感——目标不是铁板一块，可以根据实际情况协商调整
```

### 案例 2-3：激励奖金池分配

```
场景：销售团队奖金池 100 万，计划向新客户开拓倾斜

风险：老客户维护团队认为"做存量不如做增量"，可能消极维护

应用规则：
  ❌ 错误做法：一次性锁定"新客户 70 万、老客户 30 万"
  ✅ 正确做法：
     - 初始分配：新客户 60 万、老客户 30 万、浮动池 10 万
     - 触发条件（季度末）：
       若老客户流失率上升 > 5% → 从新客户池划拨 5 万到老客户维护奖
       若新客户开拓超额完成 120% → 浮动池 10 万全额奖励新客户团队

效果：两个团队都认为规则公平，"浮动池"成为季度末关注的焦点而非争议点
```

## 规则 3：向导式降噪

**定义**：任何涉及「规则复杂度提升」的方案，必须配推荐向导，把选择从 N 个压缩到 ≤ 3 个。

### 案例 3-1：SaaS 套餐选择

```
场景：产品从单一套餐扩展为 5 个套餐（免费/个人/团队/企业/定制）

风险：用户面对 5 个选项决策瘫痪，放弃购买

应用规则：
  ❌ 错误做法：平铺 5 个套餐价格表
  ✅ 正确做法——三步向导：
     Q1：您是为自己还是团队？→ 个人 / 团队
     Q2：您最需要什么功能？→ 基础够用 / API 集成 / 私有部署
     结果：
       若「个人+基础」→ 推荐免费版，"先试试，随时升级到个人版"
       若「团队+API」→ 推荐团队版，附 3 个最适合团队版的集成示例
       若「团队+私有部署」→ 推荐企业版，一键预约演示

效果：套餐选择完成率从 40% 提升到 78%，平均决策时间从 5 分钟降到 45 秒
```

### 案例 3-2：技术栈选型

```
场景：新项目启动，团队对前端框架选择有分歧（React/Vue/Svelte/Solid）

风险：选型讨论耗时 2 周，最终选了一个没人真正擅长的

应用规则：
  ❌ 错误做法：开 3 次会议逐个对比 4 个框架的优缺点
  ✅ 正确做法——三步向导：
     Q1：团队现有技术栈？→ React 系 / Vue 系 / 都行
     Q2：项目核心需求？→ 复杂交互 / 内容展示 / 极致性能
     结果：
       若「React 系+复杂交互」→ React + Zustand，推荐已有的脚手架模板
       若「Vue 系+内容展示」→ Nuxt，推荐已有的 SSR 模板
       若「都行+极致性能」→ Solid，附 3 个 Solid 上手教程链接

效果：选型讨论 1 次会议结束，附带可直接运行的脚手架
```

### 案例 3-3：大赛赛道报名（TRAE 实践）

```
场景：7 条赛道平铺展示，参赛者需逐条阅读后选择

风险：新人参赛者选择困难，可能因决策成本放弃报名

应用规则：
  ❌ 错误做法：7 条赛道 + 长简介，一页展示
  ✅ 正确做法——两步向导：
     Q1：您的身份是？→ 学生/普通用户 / 开发者/工程师 / 公益组织
     Q2：您想解决什么问题？→ 展示对应组别的赛道 slogan（≤ 3 个）
     结果：推荐「非遗传承赛道」+ 匹配 3 个官方创意 idea 作为灵感

效果：赛道匹配时间从 120s 降到 30s，报名完成率预估提升 40%
```

## 三规则联动案例

### 综合案例：公司年会奖项改革

```
场景：年会奖项从「10 个均分奖」改为「3 个差异奖 + 5 个赛道奖 + 2 个公益奖」

涉及风险：
  - 均分受益者不满（触发规则1）
  - 新奖项分类是否合理不确定（触发规则2）
  - 10 种新奖项让员工选择困难（触发规则3）

联动应用：

规则1 非现金补偿：
  人均奖金从 ¥2,000 → ¥1,500（-25%）
  补偿：获奖者家属受邀参加年会晚宴 + 定制奖杯 + CEO 手写贺卡

规则2 预留浮动：
  2 个「公益奖」作为浮动奖项，若无人报名则转为「最佳新人奖」
  预留 10% 总预算作为「现场投票惊喜奖」

规则3 向导式降噪：
  报名页 Q1：你更看重？→ 业务成果 / 团队协作 / 社会价值
  报名页 Q2：你的角色？→ 个人贡献者 / 团队 Leader
  推荐结果：不超过 2 个最适合的奖项 + 去年同类获奖者案例

效果：报名率 85%（去年均分制下仅 40% 主动关注），员工满意度提升
```

### 案例 AF-1：Python 环境标准化（规则 1：非现金补偿对冲）

```
场景：AgentForge 项目决定统一 Python 环境管理工具
        背景：apps/chaos 此前存在 conda / pip / mise 多套环境混用
        决策：强制迁移到 uv（统一工具链）
        风险：习惯了 pip/conda 的开发者可能抵触——"为什么要换？"

应用规则：

  ❌ 错误做法：发通知"下周起统一用 uv，不再支持 pip/conda"，不提供任何过渡支持

  ✅ 正确做法：
     - 现金不变（工具免费，重在降低迁移成本）
     - 非现金补偿：
       1. 提供迁移脚本 one-liner：`uv import requirements.txt`
          开发者只需跑一条命令，无需手动重建依赖树
       2. 保留 conda/pip 写法的兼容层（`pyproject.toml` 支持 pip-tools 输出格式）
          已有 requirements.txt 的团队可零改动接入
       3. 配套详细迁移文档：
          apps/chaos/.agents/rules/python.md 中有完整的"旧项目迁移路径"
          包含 conda → uv、pip → uv 两条对照路径
       4. 迁移答疑 Office Hour：前两周每天 30 分钟答疑，专人在线解答
       5. 迁移完成者获得 AgentForge 贡献者署名（写进 CHANGELOG）

效果：抵触率降低，3 周内 apps/chaos 的主项目全部完成迁移，
      且因依赖解析速度提升（uv 比 pip 快 10-100x），开发者后续满意度高于原来。
```

### 案例 AF-2：Python 3.15 适配升级（规则 2：预留浮动空间）

```
场景：AgentForge 需要将 apps/chaos/src/taolib 升级支持 Python 3.15
        背景：已有 .trae/specs/upgrade-python-3-15-adaptation/ spec
        决策：确定 Python 最低版本线 + 废弃 API 迁移时间表
        风险：Python 3.15 新增了运行时行为变更，CI 绿了不代表线上没问题

应用规则：

  ❌ 错误做法：直接切最低版本为 3.15，一刀切，无缓冲

  ✅ 正确做法：
     - 第一阶段（赛前 4 周）：基础设施适配
       做所有 import 兼容性扫描（已有脚本 check_python_compat.py）
       识别 deprecated API，生成迁移清单

     - 第二阶段（赛前 2 周）：信息公布
       发布 migration-guide.md，给团队 2 周消化时间
       在 CHANGELOG 中标记 breaking changes

     - 第三阶段（进行中）：动态微调
       预留 10% 浮动空间（1 个 minor 版本作为"安全缓冲区"）
       触发条件：若 3.15 的 breaking change 影响到 > 20% 的依赖包未释出兼容版本
                → 临时将最低版本退回到 3.14，并延长迁移窗口

       另有 10% 浮动：若发现新的 deprecated API 不在扫描范围内
                     → 从"冻结期"中抽出 1 周专项处理，不影响主计划

     - 第四阶段（赛后）：标准化
       将 Python 3.15 适配经验沉淀为 check_python_deprecations.py
       写进 apps/chaos/.agents/docs/version-tracking.md

效果：升级过程中发现 2 个隐蔽 breaking change（3.15 新增的
      dataclass transform 行为变更），均在 10% 浮动期内修复，未影响上线。
```

### 案例 AF-3：Skill 创建流程简化（规则 3：向导式降噪）

```
场景：AgentForge 规范要求新建 Skill 必须符合 SKILL.md 规范
        背景：apps/chaos/.agents/rules/skills.md 定义了 10+ 个必填字段
              （name、description、triggers、scripts、tests、SKILL.md frontmatter 等）
        决策：提供 Skill 创建标准流程
        风险：新开发者面对 10+ 字段直接放弃，或创建后不合规导致 CI 失败

应用规则：

  ❌ 错误做法：平铺 SKILL.md 规范文档，让开发者自己对照 10+ 个字段逐个填写

  ✅ 正确做法——两步向导：

     Q1：你想创建的 Skill 是什么类型的？
       → 网页内容抓取类（如 zhihu-search）
       → 工作流自动化类（如 task-execution-summary）
       → 开发工具类（如 pdf-to-markdown）

     Q2：这个 Skill 是一次性使用还是长期维护？
       → 一次性探索（快速验证假设）
       → 长期维护（需要完整测试 + CI 集成）

     结果（自动生成）：
       若「抓取类 + 一次性」：
         → 推荐使用 SPA Content Extractor 模板
         → 只填 3 个字段（name、triggers、scripts）
         → 附一个可运行的最小示例

       若「工具类 + 长期维护」：
         → 推荐完整 SKILL.md 脚手架
         → 附 check_skill_md.py 校验脚本
         → 附 CI 集成说明（skills/.validate-config.toml）

     对应落地：
       apps/chaos/.agents/templates/SKILL.md 脚手架模板
       apps/chaos/.agents/scripts/validate_skill_md.py 校验脚本
       .validate-config.toml CI 门禁配置

效果：Skill 创建不合规率从 60% 降到 5%（CI 拦截），
      开发者从"看不懂规范"变为"照着向导 5 分钟完成"。
```
