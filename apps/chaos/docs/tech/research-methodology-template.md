# 技术研究项目方法论模板

> **用途**：启动任何竞品分析 / 技术调研 / 框架构建类项目时，按本模板执行四阶段流水线。  
> **来源**：萃取自 TRAE AI 创造力大赛研究项目的完整复盘。  
> **使用方式**：复制本文件，将 `{占位符}` 替换为实际内容。

---

## 第一阶段：数据采集

### 目标
从目标源提取结构化事实数据，不进行主观判断。

### 步骤清单

- [ ] 选择抓取工具：静态优先（defuddle / WebFetch），SPA 降级至浏览器自动化
- [ ] 执行抓取：`open + wait networkidle + eval innerText`（避免 snapshot DOM 膨胀）
- [ ] 数据完整性校验：目标板块覆盖率 ≥ 90%
- [ ] 视觉留档：全页截图 + 标注截图各 1 张
- [ ] 结构化导出：JSON + 纯文本双格式

### 产出物

| 文件 | 格式 | 用途 |
|------|------|------|
| `{project}-structured.json` | JSON | 程序化引用 |
| `{project}-raw.txt` | 纯文本 | 原始数据备份 |
| `{project}-full.png` | 截图 | 视觉归档 |
| `{project}-annotated.png` | 截图 | 关键元素定位 |

### 常见陷阱

| 陷阱 | 现象 | 对策 |
|------|------|------|
| SPA 静态抓取返回空 | defuddle 只拿到标题 | 切换 agent-browser，执行 JS 后再提取 |
| snapshot 节点膨胀 | 150+ 重复 generic 节点 | 改用 `document.body.innerText` |
| Shell 跨平台报错 | `export PATH=...` 在 PowerShell 报错 | 区分阻断性与非阻断性错误，后者忽略 |

> **完整可执行模板**：上述步骤已封装为即用 Prompt 模板，包含 4 种场景（完整 SPA / 多页并行 / 静态优先 / Cloudflare 反爬），见 [spa-extraction-prompt-template.md](file:///d:/spaces/AgentForge/apps/chaos/.agents/docs/references/projects/trae/tips/spa-extraction-prompt-template.md)

## 第二阶段：洞察分析

### 目标
从结构化数据中提炼 ≥ 3 条有证据链的洞察。

### 步骤清单

- [ ] 按主题板块分组原始数据
- [ ] 每条洞察遵循 **证据链 + 推论** 结构
- [ ] 关键数字提取（总奖金、时间窗口、赛道数等）
- [ ] 生成标准 10 章报告（执行概览 → 目标背景 → ... → 改进行动）
- [ ] 可视化：至少 1 张 Mermaid 流程图 / 思维导图

### 洞察质量自检

```
每条洞察必须回答：
  1. 我看到了什么？（证据链）
  2. 这意味着什么？（推论）
  3. 这能推广到什么场景？（可复用性）

不合格示例：「TRAE 有 7 条赛道」← 只陈述事实，无推论
合格示例：「7 条赛道中有 4 条是公益方向，占总奖金 45%，
          说明用公益赛道打政策牌是结构性机会」
```

### 产出物

| 文件 | 内容 |
|------|------|
| `{project}-insight-report.md` | 10 章标准洞察报告 |

## 第三阶段：框架构建与验证

### 目标
将洞察转化为可复用的评估框架（检查清单 + 评分体系）。

### 框架设计三原则

**原则 1：权重按战略重要性分配，绝不均分**

```
正确：核心维度权重应显著高于边缘维度（如 30% vs 10%）
错误：所有维度平均分配
```

> 均分权重 = 回避判断 = 框架失去区分度。敢于分配不等权重本身就是研究结论。

**原则 2：每维度 5 个检查点**

- < 3 个：区分度不足
- \> 7 个：评分疲劳
- 5 个：覆盖核心要素，单维度评分可在 2 分钟内完成

**原则 3：评分必须可验证**

- 每个检查点配 4 级预期值，非纯主观 1-5 分
- 首次使用前必须跑边界值测试（全 1 分 / 全 5 分 / 全 3 分）
- 首次模拟评分后建议交叉验证（多人独立评分 → 对比分歧）

### 步骤清单

- [ ] 确定维度数量（建议 3-5 个）
- [ ] 分配权重（总和 = 1.0）
- [ ] 每维度定义 5 个检查点，每点配 4 级预期值
- [ ] 编写竞品分析模板（含示例评分）
- [ ] 跑边界值测试：全 1 分 / 全 3 分 / 全 5 分
- [ ] 用真实案例模拟评分

### 产出物

| 文件 | 格式 | 用途 |
|------|------|------|
| `{project}-research-checklist.json` | JSON | 结构化检查清单，含评分模板 |

### 框架 JSON 结构模板

```json
{
  "research_dimensions": {
    "{dimension_key}": {
      "name": "{维度名称}",
      "weight": 0.3,
      "checkpoints": [
        {
          "id": "{CP-01}",
          "name": "{检查点名称}",
          "expected_values": ["{第1级}", "{第2级}", "{第3级}", "{第4级}"],
          "example": "{参考示例}"
        }
      ]
    }
  },
  "competitor_analysis_template": {
    "competitor_name": "",
    "score_summary": {},
    "key_insights": []
  },
  "scoring_method": {
    "scale": "1-5",
    "overall_calculation": "各维度得分 × 权重 之和"
  }
}
```

## 第四阶段：优化与机会评估

### 目标
基于框架评分，输出可落地的优化方案和机会清单。

### 优化方案四段式汇报模板

```
## {方案名称}

### 现状问题
{用数据/评分描述当前问题，不凭感觉}
- 检查点 {ID}：得分 {X}/5，原因：{...}

### 优化方案
{具体的新方案，包含可操作细节}
- 分类方式 / 奖金分配 / 流程调整

### 预算影响
{必须算账}
| 项目 | 当前 | 优化后 | 变化 |
|------|------|--------|------|
| ... | ... | ... | ... |

### 预期收益
{量化改善}
| 指标 | 当前 | 优化后 | 变化 |
|------|------|--------|------|
| ... | ... | ... | ... |
```

### 产品机会评估矩阵

```
            高政策契合
                │
        蓝海    │    战略
      （优先）  │   （长期）
  ──────────────┼────────────── 高变现潜力
       （回避）  │   （红海）
                │
            低政策契合
```

### 评分维度（5 维）

| # | 维度 | 说明 | 权重建议 |
|---|------|------|----------|
| 1 | 社会影响力 | 受益人群规模与需求刚性 | 25% |
| 2 | 政策契合度 | 与国家战略对齐度 | 25% |
| 3 | 技术可行性 | 用目标工具可实现的难度 | 20% |
| 4 | 蓝海程度 | 赛道拥挤度 | 15% |
| 5 | 变现潜力 | 可持续运营能力 | 15% |

### 步骤清单

- [ ] 对框架中得分最低的维度做根因分析（具体到检查点级别）
- [ ] 每个优化方案填写四段式汇报模板
- [ ] 预算影响优先选择「零增长内部分配」方案
- [ ] 对可选方向按评估矩阵打分，输出 P0/P1/P2 优先级
- [ ] 每个方向标注「回避信号」（如红海赛道、技术不可行）

### 产出物

| 文件 | 内容 |
|------|------|
| `{project}-optimization-report.md` | 优化方案汇报材料（含 Mermaid 图表） |
| 机会评估结果 | P0-P2 方向清单 + 评分矩阵 |

## 收尾：萃取与归档

### 归档清单

| 阶段 | 动作 | 目标位置 |
|------|------|----------|
| 完整留档 | 复制全部有效产物 | `.archive/{project}-{date}/` |
| 可复用萃取 | 提炼方法论/公式/原则 | `.agents/docs/references/projects/{project}/` 或 `docs/tech/` |
| 清理 | 删除 `.temp/` 中已归档文件 | — |

### 归档自检

- [ ] `.temp/` 留存文件 ≤ 原始数量的 30%
- [ ] 一年后接手者能通过归档文件独立复现研究
- [ ] 萃取文档中无具体案例名，已替换为通用表述
- [ ] 归档目录文件清单已记录

### 信息递减链

```
原始数据（100%） → 洞察报告（30%） → 复盘报告（15%） → 萃取文档（5%）
                    ↑                    ↑                  ↑
                 删细节留结论         删过程留决策         删案例留公式
```

## 附录 A：工具链速查

| 场景 | 推荐工具 | 替代方案 | 注意事项 |
|------|----------|----------|----------|
| 静态网页抓取 | defuddle | WebFetch | 轻量优先，失败再升级 |
| SPA 动态抓取 | agent-browser | Playwright | 内置 wait networkidle |
| 文件写入（Windows） | Write 工具 | 独立 .py 文件 | 避免 Python -c 多行字符串 |
| 评分逻辑验证 | Python 单行脚本 | 手算 | 结果可复现 |
| 批量文件操作 | Python shutil | 手动复制 | 降低错误率 |
| 任务追踪 | TodoWrite | 无 | ≥ 3 步任务必须用 |

## 附录 B：团队同步摘要模板

**用途**：研究计划确定后，生成 1 页摘要用于团队同步/站会/邮件。

**模板**：

```
# 研究计划同步摘要：{项目名}

> 基于 [{完整计划文件}] 精简 | {日期}

---

## 一句话
{一句话说清：研究什么、输出什么}

## 对象范围
| 对象 | 侧重点 |
|------|--------|
| {名称} | {一句话定位} |

## 阶段计划
| 阶段 | 做什么 | 产出 |
|------|--------|------|
| ① 数据采集 | {采集维度和来源} | {产出格式} |
| ② 洞察分析 | {横向对比目标} | {≥ N 条洞察} |
| ③ 框架构建 | {框架规模和维度} | {评估清单} |
| ④ 优化评估 | {基于评分的改进} | {P0-P2 方案} |

## 核心问题（3-5 个）
1. {差异化问题 1}
2. {差异化问题 2}
3. {差距问题}

## 预期输出
- {可复用产出 1}
- {可复用产出 2}
- {P0 改进方向}

## 需要对齐
- {待讨论的范围/权重/分工问题}

---

*1 页摘要 | 团队同步用 | 完整计划见 `{链接}`*
```

**使用要点**：
- 控制在 1 页内（50 行左右），超出则说明计划本身太复杂
- 「需要对齐」段是摘要的核心价值——不是汇报已完成的工作，而是抛出待决策的问题
- 每条对齐项应该是选择题（A or B），而非开放式讨论
